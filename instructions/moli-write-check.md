# moli-write-check — 自媒体文案合规检测与改写

面向小红书 / 公众号 / 抖音等中文平台的发布前合规检查:确定性词库检测(L1 广告法极限词、L2 平台违禁词)+ Agent 上下文风险判断(L3),产出合规报告与可直接发布的改写稿。

## 工作流

```
 setup check → intake → detect (L1/L2)
                          ↓
                    context review (L3)
                          ↓
                       report
                          ↓
                用户确认是否改写
                          ↓
              rewrite → re-check → deliver
```

---

## Step 1: Setup Check

| 依赖 | 用途 | 验证 |
|---|---|---|
| Python 3.10+ | 运行检测脚本 | `python3 --version` |

检测脚本零第三方依赖,无需 pip 安装。脚本路径:

```bash
DETECT="$MOLI_SKILLS_DIR/moli-write-check/scripts/detect.py"
```

## Step 2: Intake

1. **文案来源**:用户粘贴的文本,或文件路径。两者都没有则请用户提供,不要自己编造。
2. **目标平台**:决定加载哪套平台词库。
   - 用户明确说了平台 → 只扫该平台(`--platform xiaohongshu|wechat|douyin`)
   - 未说明 → 默认扫全平台,**不要追问**;报告中按平台标注风险来源
3. **内容类型**(仅影响 L3 判断,缺失则按普通图文处理):笔记/文章/视频口播稿/直播话术。

## Step 3: Detect(L1/L2 确定性检测)

```bash
python3 "$DETECT" --file <文案路径> --platform all
# 或: python3 "$DETECT" --text "<文案>" --platform xiaohongshu --format json
```

- 退出码 0=未命中,1=有命中,2=参数错误
- 文本输出按 违规(必改)/ 高风险(建议修改)/ 谨慎(结合语境) 三级分组,含行号定位与替换建议
- **词库只覆盖词面风险**。命中≠必改(谨慎级),未命中≠合规(交给 Step 4)

## Step 4: Context Review(L3 上下文判断,Agent 负责)

逐条核对以下清单,每条发现都标注:位置、风险类型、严重度(block/risk/caution)、理由。词库命中的词条如果语境安全可降级,在报告中说明。

| # | 检查项 | 判断要点 |
|---|---|---|
| 1 | 医疗/功效宣称 | 非药品、医疗器械不得宣称治疗功效;化妆品美白/祛斑/防脱需特殊化妆品注册;普通食品不得提疾病 |
| 2 | 金融收益承诺 | 稳赚、保本、预期收益、历史业绩引用——是否持牌、是否有风险提示 |
| 3 | 软广未标注 | 商业合作内容是否声明"广告/合作/赞助";是否规避平台报备机制 |
| 4 | 贬损对比 | 是否直接贬低竞品或使用"比 XX 好"等对比表述(广告法第十三条) |
| 5 | 引流导购 | 是否暗示绕过平台到站外交易(变体话术:威❤、微❤、+V 等拆字/谐音) |
| 6 | 价格误导 | "原价"是否有真实成交依据;赠品/最低价承诺是否可兑现 |
| 7 | 数据与背书 | 引用的销量、排名、检测结果是否有可查证来源 |
| 8 | 特殊人群 | 未成年人、孕产妇相关宣称是否有依据;保健品是否暗示替代药品 |
| 9 | 权益表述 | "永久/终身/免费"等承诺是否在条款中可兑现 |

## Step 5: Report

汇总 L1/L2/L3 结果,写入(遵循项目的版本目录约定,默认 `docs/moli/`):

```
docs/moli/compliance-v1/
├── report.md      # 合规报告
└── rewritten.md   # Step 6 产出后写入
```

`report.md` 结构:

1. **结论**:可发布 / 修改后可发布 / 不建议发布(存在 block 级未改即"修改后可发布"以下)
2. **统计**:L1/L2 命中按严重度计数;L3 发现计数
3. **明细**:三级分组列出全部发现——每条含位置、原文摘录、风险说明、修改建议
4. **遗留风险**:用户选择保留的 caution 项及其后果提示

## Step 6: Rewrite(用户确认后执行)

生成 `rewritten.md` 合规改写版:

- **保留原意与文风**——改的是风险表述,不是重写文案
- 每处改动给出 `原文 → 改后` 对照及一句理由
- 拿不准如何改的(涉及事实性承诺等),保留原文并用 `<!-- 待确认: 原因 -->` 标记,交给用户决定
- 平台规则存在灰度的,倾向保守改法并说明

## Step 7: Re-check

对 `rewritten.md` 重跑 Step 3 检测:`block` 与 `risk` 清零即通过;`caution` 项逐条向用户确认保留或修改。未清零则回到 Step 6。

## Step 8: Deliver

告知用户:`report.md` 与 `rewritten.md` 路径、最终结论、遗留的 caution 项清单。

---

## 原则

1. **脚本是工具,不是流程**——detect.py 只做确定性词面匹配;语境判断、改写、结论由 Agent 负责
2. **文案不出本机**——词库检测纯本地执行,不调用任何外部检测 API
3. **词库是起点**——平台规则更新频繁,词库见 `moli-write-check/references/wordlists/`,修改时同步维护其 README 的约定
4. **报告版本可追溯**——同一文案多轮检测走 `compliance-v1/`、`compliance-v2/` 递增,不静默覆盖
5. **不替用户做商业决定**——caution 级风险一律交用户拍板,Agent 只提供后果说明
